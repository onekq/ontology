Conflict 1 of 10
Parent decision — resolve first

Are MRN-100234 and MRN-100891 the same patient?

Same DOB, same SSN last 4, same insurance member ID, a misspelled name variant — and a duplicate-check flag from 2023 that was never actioned (REQ-303).

Recommended — FHIR, used precisely
Use Patient.link exactly as FHIR intends: MRN-100234 (the more clinically complete record) keeps type: replaces pointing at MRN-100891; MRN-100891 gets type: replaced-by pointing back. Any query for "the current patient" resolves to MRN-100234 — which is also what fixes Conflict 5 automatically, without new vocabulary.
Depends on Conflict 1

MRN, SSN, and insurance member ID don't cleanly identify one person each

Tomas Reyes has no SSN on file (a minor). Family-plan member IDs share a prefix across dependents, and a 2024 lab result was routed to the wrong family member because of it.

Recommended — FHIR + domain
Keep all three as independent Patient identifiers — FHIR doesn't require all three either. Add a domain FamilyPolicyGroup class linking Elena and Tomas Reyes explicitly, so "shares a member-ID prefix with" becomes a queryable fact instead of something a human has to notice from the ID string itself.
Conflict 3 of 10 — highest stakes

A condition entered in error is still being counted as active

COND-8802's clinicalStatus is "active." Its verificationStatus is "entered-in-error." The population-health reporting system reads only the first field.

Recommended — FHIR, used precisely
Both fields already exist in FHIR precisely to prevent this. The fix isn't new vocabulary — it's a rule that any consumer treating clinicalStatus as meaningful must first check verificationStatus is not entered-in-error or refuted. This is the conflict where the ontology was already capable of representing the truth; a downstream system just wasn't using the fields FHIR gives it.
Conflict 4 of 10

A condition's billing code and clinical code have drifted apart

COND-8801's ICD-10 code was refined in 2019 guidance updates; its clinical terminology mapping was never re-synced and is now broader/less specific.

Recommended — FHIR
Keep both codings on the same Condition.code — FHIR's CodeableConcept is designed to carry multiple codings for one concept. Add a domain codingLastSynced date so staleness is a visible, queryable fact rather than a silently-trusted mapping.
Conflict 5 of 10 — resolved by Conflict 1

The Penicillin allergy disappears when Dana's more recently active record is queried

ALG-201 is recorded only against MRN-100234.

Recommended — already settled in Conflict 1
No new work needed: once Patient.link correctly marks MRN-100234 as the surviving record, any system that respects the link resolves to it — and its AllergyIntolerance record — automatically. This is exactly why Conflict 1 was resolved first, in dependency order.
Conflict 6 of 10

Does "active" mean the patient is admitted, or that a condition is current?

Nursing and Billing/Coding use the same word for two different real FHIR fields.

Recommended — no invention needed
Nursing's meaning is Encounter.status. Billing's is Condition.clinicalStatus. Both already exist as distinct real FHIR fields — the ambiguity was purely in the shared English word, not in any modeling gap.
Conflict 7 of 10

ENC-5001 is still "in-progress" weeks after it clinically ended — and Front Desk's "encounter" isn't FHIR's

Nobody marked the encounter complete. Separately, Front Desk uses "encounter" to include no-shows, which FHIR's real Encounter resource never covers.

Recommended — FHIR + domain
ENC-5001 should have status: finished with a real period.end — flag any in-progress encounter with a stale period.start as needing closure, a queryable pattern rather than a silent staff oversight. Separately, give Front Desk's broader meaning its own domain ScheduledSlot class — FHIR's Encounter was never meant to include no-shows, so forcing it to would be wrong, not just imprecise.
Conflict 8 of 10

A data-sharing consent is being used for a purpose it wasn't scoped for

CONSENT-401 covers "billing." Referral sharing has been proceeding under it for "care coordination" anyway.

Recommended — FHIR
Require the requested purpose of use to be checked against the Consent resource's actual recorded scope before any data share — re-verified per use, not assumed valid because a consent of some kind exists on file. A consent record existing at all isn't the same fact as it covering the specific use being made of it.
Conflict 9 of 10

The care plan review checkpoint doesn't reconcile medications

"Confirm patient contacted" passes regardless of whether the medication list was actually checked.

Recommended — domain-specific
Add a reconcilesMedicationList: false flag on this checkpoint, same pattern as every prior vertical's checkpoint-gap conflict (manufacturing's QC check, retail's returns inspection, finance's KYC refresh). A checkpoint's name implying more than it verifies is a recurring, cross-domain failure mode — not a healthcare-specific one.
Conflict 10 of 10

Scheduling and specialty intake disagree on referral turnaround

Scheduling: 3 business days. Intake's own tracking: 6 business days average. Never reconciled.

Recommended — domain-specific
Model both as separate, timestamped ReferralSLA instances rather than reconciled into one number — same principle as every prior vertical's cross-team operational-disagreement conflict. The gap between stated and actual turnaround is the fact worth keeping visible, not averaging away.
